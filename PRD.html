1. 背景与目标

1.1 问题背景

中小外贸企业在出海物流环节面临三个痛点：

  • 多式联运方案难规划：义乌到洛杉矶需要公路→河运→海运多段衔接，不同运输方式成本/时效/碳排放差异大，企业缺少帕累托前沿对比工具。
  • 报关单证专业门槛高：HS 编码归类需查阅海关税则，不同商品的监管证件/认证要求/关税税率不同，错误归类导致退运或罚款。
  • 信息分散、多系统切换：运输、报关、订舱、追踪分散在不同系统，数据重复录入，缺乏统一协同入口。

1.2 产品决策

构建一个多 Agent 协同系统，用户输入自然语言需求（文字或发票图片），系统自动调用 4 个专业 Agent 协同完成从国内运输到报关单证的全链路方案输出。

1.3 可观测目标

  • 用户输入"义乌发 20 吨日用百货到洛杉矶，省钱优先"，3 秒内返回 4 条候选路线 + 报关单草稿 + HS 编码 + 合规风险提示。
  • 用户上传发票图片，系统自动 OCR 提取商品信息并完成归类，无需手动填写商品名。
  • 用户在地图上看到不同方案的路线差异，点击切换方案时地图实时更新。

2. 范围与边界

2.1 P0 核心流程

入口条件：用户在网页输入起运地 + 目的港 + 货重 + 优先级，或上传发票图片。

P0 动作：

  1. 协调器识别用户意图（单环节 vs 全流程）
  2. 运输 Agent 生成多式联运路线方案（帕累托前沿）
  3. 报关 Agent OCR 提取商品 → HS 编码归类 → 生成报关单草稿 → 合规校验
  4. 订舱 Agent 查询船期 → 推荐最优订舱方案
  5. 追踪 Agent 生成运单 → 模拟状态查询
  6. 前端渲染：方案卡片 + 地图路线 + Agent 输出汇总

完成证据：页面中间栏显示方案卡片（含成本/时效/中转次数/碳排放），底部显示 4 个 Agent 的输出摘要，右侧地图画出选中方案的彩色路线。

2.2 P1 辅助功能

  • 季节性系数调整（旺季查验率/运价上浮）
  • geopy 经纬度距离计算（自动选最近港口）
  • 发票上传 → OCR 预处理 → 字段存 context → 下游 Agent 复用
  • DeepSeek LLM 智能意图解析（正则失败时降级到 LLM）

2.3 明确排除

  • 不对接真实海关单一窗口（报关单为草稿，不实际申报）
  • 不对接真实船公司 API（船期数据为模拟）
  • 不对接真实物流追踪 API（运单状态为模拟状态机）
  • 不做用户注册/登录/权限管理
  • 不做支付/结算功能

4. 功能需求

4.1 协调器入口层 P0 已实现

目的

作为系统统一入口，识别用户意图，决定调用哪些 Agent 及执行顺序，并在图片输入时做 OCR 预处理。

处理规则

规则行为
图片检测query 以 .jpg/.jpeg/.png/.bmp 结尾时触发 OCR 预处理
OCR 预处理PaddleOCR 提取文本 → DeepSeek-VLM 结构化为 cargo_name/tonnage/unit_price → 存入 pre_context
意图识别关键词匹配优先（确定性高、免费），正则失败时降级到 DeepSeek LLM
执行模式single：只调 1 个 Agent；pipeline：按 [transport→booking→customs→tracking] 顺序串联
context 传递pipeline 模式下，前一个 Agent 的输出写入 context，后一个 Agent 从 context 读取
OCR 降级OCR 失败（无图片/API 错误）→ 静默回退到文字 query，不阻断流程

异常处理

  • 无可用 Agent → 返回"无法处理该需求"提示
  • 单个 Agent 执行异常 → 标记 error 状态，不阻断其他 Agent 执行
  • OCR 模块不可用 → 跳过预处理，文字 query 直接传给下游

4.2 运输路线 Agent P0 已实现

目的

为用户生成国内段多式联运路线方案，提供帕累托前沿对比，让用户在成本与时效间做权衡。

节点与边

类型节点示例数量
origin（起运地）义乌、成都、北京、苏州、广州、深圳、西安、郑州13
sea_port（海港）宁波港、上海港、深圳港、广州港、青岛港、天津港6
river_port（河港）杭州港1
rail_hub（铁路站）义乌西、金华西、宁波北仑、郑州东、北京南、广州南6
airport（机场）浦东机场、双流机场2

边覆盖公路、铁路、河运、海运、空运 5 种运输方式，当前 40 条边。

成本四层模型

层级含义计算依据
L1 干线运费各段运输费用之和距离 × 单价 × 旺季系数
L2 中转衔接中转装卸/仓储/换装费每中转一次加固定费率
L3 时间滞期在途时间的机会成本总时效 × 时效惩罚率
L4 风险准备金查验/扣关/延误风险旺季风险准备金率 × L1

帕累托前沿

所有候选方案按 (cost, hours) 双目标排序，标记非劣解为 is_pareto=True。标签规则：

  • 成本最低 → tag="最省钱"
  • 时效最短 → tag="最快"
  • 帕累托前沿上非极端解 → tag="折中(推荐)"

自动选最近港口

全流程模式下用户输入国外目的地（如洛杉矶），系统自动为起运地选最近海港：

  1. 从 nodes.json 查起运地经纬度
  2. Haversine 公式算到所有 sea_port 的距离
  3. 选最近的返回
  4. geopy 在线服务作方案 B（节点库无坐标时）
  5. 硬编码城市→港口映射作方案 C（兜底）

季节性调整

月份旺季系数查验率影响运价影响
9-12 月（旺季）cost ×1.35, hours ×1.50查验率上升运价上浮
1-2 月（春节）cost ×1.20, hours ×1.30部分港口停摆舱位紧张
3-8 月（淡季）cost ×1.00, hours ×1.00正常正常

4.5 追踪 Agent P0 占位版

目的

创建运单号，查询运输状态，检测异常并给出处理建议。

当前实现

5. 共享规则与计算模型

5.1 成本计算公式

total_cost = L1 + L2 + L3 + L4

L1 = Σ(段距离 × 段单价) × 旺季系数
L2 = 中转次数 × 中转费率
L3 = 总时效 × 时效惩罚率
L4 = 旺季风险准备金率 × L1

5.2 季节性系数

月份cost 系数hours 系数查验率风险准备金率
9, 10, 11, 121.351.50上升5%
1, 21.201.30部分停摆3%
3-81.001.00正常0%

5.3 帕累托前沿判定

方案 A 支配方案 B，当且仅当：A.cost ≤ B.cost 且 A.hours ≤ B.hours 且至少一个严格小于。不被任何其他方案支配的方案标记为帕累托前沿。

5.4 OCR 降级链

优先级来源触发条件
1coordinator_ocr（协调器预处理）context.from_image + context.cargo_name 存在
2upstream_context（上游 Agent）context.cargo 存在
3paddle_ocr+vlm输入为图片路径
4text_input输入为文字（正则+关键词匹配）

5.5 HS 编码选择降级

步骤行为降级条件
检索 Top-3 候选关键词匹配打分Chroma 启用时走向量检索
LLM 选择最优DeepSeek 在候选中选 1无 API Key 或调用失败 → 返回首个候选
结果校验origin/destination 必须在节点列表内不在列表 → 返回 None → 触发自动选港

5.6 Agent 执行异常处理

  • 单个 Agent 抛异常 → 标记 status=error，summary 记录错误信息，不影响其他 Agent
  • Agent 超时 [TBD，建议 30 秒] → 标记 timeout
  • 所有 Agent 均失败 → 返回整体 error，提示用户重试
